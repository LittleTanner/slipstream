# Porting Slipstream to iOS

Read `DEV-LOOP.md` and `DECISIONS.md` first. This file is about moving the game to Swift
without losing what the measurements bought.

**First practical step: copy `CLAUDE-for-the-port.md` into the Swift project as its
`CLAUDE.md`.** A fresh repo has none of this context, and an agent working without it will
rewrite rather than reproduce.

The whole strategy is one sentence: **keep the JavaScript sim alive as a reference oracle, and
make the Swift sim prove it matches, frame by frame, before anything else is judged.**

---

## What ports, and what does not

| | ports | why |
|---|---|---|
| `Sim` IIFE (`index.html:571-4470`) | **almost line for line** | deterministic and DOM-free. 3901 lines. Verified by grep: zero `document`, `canvas`, `localStorage`, `performance`, `Math.random`, `setTimeout` or `requestAnimationFrame`. The only `window.` hits are the word "window" in comments (a team car's, a tolerance one) | 
| `tools/parts.js`, the stat model | directly | plain data and arithmetic |
| `golden.json`, `port/` | as fixtures | they are data, not code |
| the view IIFE | **rewritten** | canvas + touch becomes SwiftUI. Do not translate it. `docs/SCREENS.md` is what it must be rewritten INTO: all 17 screens, what each is for, and the HUD |
| `Store` / `window.storage` | **deleted** | browser scaffolding. On iOS this is `@AppStorage` for the ladder and SwiftData for history — the `Store` block already carries a PORT NOTE saying why the history blob is wrong for the real app |
| the debug gesture panel | rewritten, kept | it has earned its place three times |

### The one clock dependency, and it will bite you if you miss it

The sim is otherwise clock-free, but `dailyKey(now)` and `dailyNumber(now)` fall back to
`new Date()` when no `now` is passed. Both are **injectable**, and only the view ever calls them
without an argument — which is why `golden.json` is completely clock-free and CI does not break
at midnight. Keep that discipline: the sim takes the date, it never asks for it.

**It is UTC on purpose.** `DAILY_EPOCH` is `Date.UTC(2026, 0, 1)` and every read is
`getUTCFullYear` / `getUTCMonth` / `getUTCDate`, so nobody in a later time zone gets tomorrow's
course early and posts the layout. On iOS that means a `Calendar` with `timeZone` pinned to
`TimeZone(identifier: "UTC")` — **not** `Calendar.current`, which is local and would hand every
rider a different daily challenge and a different streak. This is the single easiest thing in the
whole port to get subtly, silently wrong.

**Do not restructure the single HTML file to make porting easier.** The extraction already
works: `node tools/extract.js` slices the sim out cleanly, and that slice is what every harness
runs against.

## The order of work

1. **Port the PRNG and course generation first, and get `golden.json`'s course section
   passing.** Everything downstream is worthless until a seed draws the same road. This is the
   single most fragile part of the port — see the PRNG rule below.
2. **Port `stepRider` and `step`, then run `port-verify` until it passes.** Do not move on while
   any trace diverges. A 0.0001% error in one constant shows up within nine seconds of race time.
3. **Port `settle`, the GC and the ladder.** Now `golden.json`'s 1590 checks should pass.
4. **Only then start the SwiftUI view.** A view built on a sim that is 2% off will be tuned to
   compensate for the 2%, and you will never find it afterwards.

## The conformance kit

Generated by `node tools/port-export.js`, checked by `node tools/port-verify.js`.

```
port/constants.json   every CFG value as data (105 of them)
port/api.json         the module surface: 67 exports, the entry points, the full input struct,
                      117 rider fields, the race fields, SAVE_KEYS, the event queue, and the
                      units warning. THIS IS THE INTERFACE SWIFT HAS TO IMPLEMENT
port/protocol.json    the harness contract: timestep, input policy, sampling, tolerances
port/trace.json       per-rider dist/speed/energy sampled once a second through three races
```

`api.json` is generated by **inspecting the live module**, not hand-written — shapes are observed
(`function/3` is a real arity, `array[8] of object` is a real length), and the field dictionaries
come from a mountain stage and a time trial stepped a thousand frames, so fields that only exist
once something has happened (`swingGap`, `cadSpeed`, `gearIdeal`, `ttHold`) are all present. A
hand-written interface doc is stale the first time someone adds a field, and a stale one is worse
than none because it is believed.

Three things in it that are easy to miss and expensive to discover:

- **`step(race, dt, input)` takes `input = null`** to let the sim's own AI ride the player. That
  is what `ladder.js` and `dominance.js` do, and it is exactly why neither can see any mechanic
  that needs player input.
- **`race.events` is a queue the view drains and empties each frame**, entries of
  `{ t: string, c: colourKey }`. The sim never draws; it says what happened and the view decides
  how. Keep that split — it is the reason the sim ports at all.
- **The sim works in metres and seconds; the view multiplies by `SCALE` (100)** for display. On
  screen kilometres are not sim metres. Do that conversion in exactly one place in Swift;
  `DECISIONS.md` has a whole section on the three display scales disagreeing.

**`golden.json` says what a race RESULTS IN. `port/trace.json` says what it DOES.** The golden is
the right contract for "did I break the game" and the wrong one for "my Swift sim is 0.3s off and
I have no idea where" — a result is the sum of 30,000 frames, and when it differs every frame is
a suspect. The trace converts *the answer is wrong* into *frame 14,220 is wrong*.

The three cases are chosen to stress different paths: a flat stage, a mountain stage (climbs,
descents, switchbacks) and a time trial (start intervals, cadence, gearing).

### Port `tools/port-verify.js` before writing your own comparison

It is fifty lines and it already encodes the decisions that matter:

- **Stop at the first mismatch.** Every later sample is an echo of the first, and a wall of 400
  divergent lines hides the one that matters.
- **Check the constants separately and first.** Drift there makes every other number a lie.
- **Compare in rider order**, taken from the fixture, not from a name lookup.
- **Use the tolerance, not equality.** `1e-4` absolute — far tighter than any real behavioural
  difference, far looser than last-bit float noise between languages.

### Regenerate whenever the sim changes

`port/` moves whenever `golden.json` moves. `port-verify` fails loudly when it is stale, which is
deliberate: a conformance fixture nobody re-checks rots, and a rotten fixture is worse than none
because the port would be chasing a divergence from a sim that no longer exists.

## Rules that will bite a port

**Fixed timestep, always.** The sim is deterministic only at `fixedDt` (1/120 s). A variable
frame time is a different simulation, not a faster one. Accumulate real time and step in whole
`fixedDt` slices; never pass a display delta.

**The PRNG order is part of the specification.** Course generation consumes seeded mulberry32 in
a fixed order. Adding, removing or **reordering** one `R()` call inside course generation changes
every course from that point on. Derive new values from existing draws instead of taking fresh
ones. This rule has its own section in `DEV-LOOP.md` because it has been broken before.

**Read the constants, do not retype them.** `port/constants.json` exists so 105 numbers have one
source of truth. Several are load-bearing in ways their name does not suggest, and the reasoning
lives inline beside each in `index.html`:

- `swingCut` 0.09 — every value above 0.12 breaks the wheel-suck escalation, and **the mechanics
  suite gives a false green on it**. Verify against the golden.
- `gearHyst` 0.45 — hard ceiling of 0.785, above which a one-gear error can never light a
  chevron.
- the TT target's `Math.max(strokeTempo, ...)` floor — without it the rule spirals to a
  standstill; measured once at 1799s against a normal 108s.
- `easeCut` 0.45 is deliberately **not** `swingCut`, because a rival's swing is automatic and
  yours is a decision.

**Float ordering.** A few places (`Math.hypot`, exponentiation) may associate differently in
Swift. That is what the `1e-4` tolerance is for. If you need exactness, match the JS expression
shape rather than "simplifying" the algebra — the simplification is where the drift enters.

## What the harnesses can and cannot see

This is the part most worth carrying over, because every one of these was learned by being
wrong first. **A harness that supplies the missing piece cannot see it missing.**

| harness | sees | is BLIND to |
|---|---|---|
| `golden.json` / `verify.js` | course draw, finishing order, times, points, money | anything on the AI-driven player path — it drives the player through `input` |
| `ladder.js`, `dominance.js` | balance across divisions and parts | anything needing player input; they set `you.you = false` and use the AI path |
| mechanics suite | one promise per mechanic | **swing constants — documented false green.** `refusal.test.js` is the only file that sees a swing change |
| `gearing.js` | whether chasing the ideal gear pays | nothing, if its rider taps the target exactly: that pins `hold` at 1.0 and makes the band unmeasurable |
| `aiswing.js` | drop-back duration | produced **two** bogus figures (11.91s, 39.07s) that were written into docs as defects before anyone checked the harness |
| browser suites | the DOM contract | anything the injected shim provides — this hid a total save failure for 30+ builds |

Concretely, for the port: **write the Swift conformance test so it does not inject anything the
real app does not have.** The `window.storage` bug is the whole argument. If a test needs a shim,
ask what the shim stands in for and whether anything checks the real thing exists.

## Keep the oracle

Do not delete the JavaScript once Swift works. Keep it as the reference implementation:

- When a Swift behaviour looks wrong, you can run the same seed here in seconds and see whether
  the sim or the port is at fault. Without it, every question becomes an argument.
- `golden.json` becomes a **specification** rather than a regression test — the definition of
  what Slipstream does, in a form both languages can be checked against.
- Balance work (`ladder.js`, `dominance.js`, `gearing.js`) is far cheaper headless in Node than
  in a simulator, and none of it needs a view.

The reasonable end state is a small repo that holds the JS sim, the harnesses and the fixtures,
and a Swift app that must pass them.

## Before the port is "done"

- `port-verify` passes on all three traces.
- `golden.json` passes 1590/1590 against the Swift sim.
- `ladder.js` and `dominance.js` re-run against Swift give the same shape (on-path 3.63 to 5.30,
  worst rung gain 1.47, 0 dominant parts).
- Saving works **on a real device with nothing injected**, and survives a cold launch.
- StoreKit is wired. `unlockCareer()` is the ONLY function that grants the career and is the
  single seam to replace: `Product.purchase()`, verify, `finish()`, then set `full`. It also
  needs **Restore Purchases**, which the App Store requires and which the prototype cannot test.
